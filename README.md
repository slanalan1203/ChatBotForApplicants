# ChatBotForApplicants

## 1. Контекст проекта  
### 1.1 Бизнес-задача  
-  Проблема: Абитуриенты и их родители часто задают однотипные вопросы, создающие ненужную нагрузку на штат приемную приемную комиссию. Информация находится в неудобном формате и самим сотрудникам не удобно с ней работать.
-  Почему именно чат-бот / RAG-система имеет смысл.
  1) Классический FAQ не может покрыть все вопросы столь общирной темы как поступление в вуз. Также чат бот может поддерживать смешанность вопросов(например: каковы сроки поступления и какие олимпиады дают БВИ)
  2) RAG позволяет давать ответ только на основе источников => риск ошибок ниже, чем у классических LLM
-  Критерии успеха: Снижение числа однотитипных вопросов. Бот корретно отвечает на вопросы из "Золотого набора". 

### 1.2 Целевая аудитория и пользователи  
-  Пользователи
   1) Абитуриенты
   2) Родители абитуриентов
   3) Сотрудники приемной комиссии
-  Сценарий использования: текстовый чат в Telegram в формате вопрос -> ответ+источники
-  Нагрузка 50-100 пользователей в день. Пиковые часы: вечер будних дней, выходные
-  
### 1.3 Ограничения и допущения  
-  Что нельзя делать:
   1) Чат-бот не дает юридических консультаций
   2) Не собирает персональные даннык(ФИО/паспортные данные/телефон и тд)
-  Допущения:
   1) Все документы берутся исключительно из официальных источников(не заглядываем на сайты консультация поступление и прочее)
   2) Обновление базы знаний происходит периодически(не в реальном времени)

## 2. Архитектура решения  
### 2.1 Общая схема  
-  Архитекутра: Telegram чат -> BotApi(Aiogram) -> RAG -> Векторная DB(FAISS) + JSONL чанки -> LLM -> готовый ответ 
-  Компоненты и роли:
   1) Telegram чат: принимает сообщения
   2) BotApi: long-polling, авторизация в Telegram по токену
   3) RAG: эмбеддинг запроса -> retriever -> Сбор контекста+промт -> generation
   4) Векторная DB(FAISS): Локальное хранение, Поиск по Эмбеддингам чанков
   5) JSONL чанки: хранение текста и метаданных
   6) LLM: Генерация ответа
- Буду спрашивать со всех: где лежит бд, когда мы в неё стучимся, где лежит промпт, в каком порядке обрабатываем пользовательские запросы?
  1) БД лежит локально(FAISS)
  2) Стучимся при вопросе и обновлении данных
  3) В репозитории проекта
  4) в порядке: стром эмбеддинг -> retrieval -> Cбор контекста -> generation -> возвращаем ответ

### 2.2 Хранилище знаний / документооборот  
-  Источники знаний: Документы и правила приема ВШЭ(https://ba.hse.ru/docs), РСОШ(https://rsr-olymp.ru/) 
-  Документооборот. Загруженные документы проходят через очистку от ненужной информации с помощью LLM с сохранением метаданных(название, URL, страница)
-  Обработанные документы преобразуются в векторные представления и сохраняются в соответствующей веткорной базе данных

## 3. Данные и качество знаний  
### 3.1 Сбор и предобработка данных  
-  Форматы: PDF-документы + HTML страницы
-  Шаги предобработки:
   1) Скачивание нужных PDF(HTML)
   2) Извлечение текста
   3) Очистка текста(ручная + LLM)
   4) Добавление метаданных
   5) Преобразование данных в Чанки
-  Метаданные
   1) Ссылка на документ(страницу)
   2) Название источника
   3) Год приемной кампании
   4) Тип документа(привила приема/учет БВИ/приложение)
   5) Город(Москва/Санкт-Петербург/Нижний Новгород/Пермь)
   6) Размер Чанка
   7) ID чанка
