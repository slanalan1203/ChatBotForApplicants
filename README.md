# ChatBotForApplicants

## 1. Контекст проекта  
### 1.1 Бизнес-задача  
-  Проблема: Абитуриенты и их родители часто задают однотипные вопросы, создающие ненужную нагрузку на штат приемную приемную комиссию. Информация находится в неудобном формате и самим сотрудникам не удобно с ней работать.
-  Почему именно чат-бот / RAG-система имеет смысл.
  1) Классический FAQ не может покрыть все вопросы столь общирной темы как поступление в вуз. Также чат бот может поддерживать смешанность вопросов(например: каковы сроки поступления и какие олимпиады дают БВИ)
  2) RAG позволяет давать ответ только на основе источников => риск ошибок ниже, чем у классических LLM
-  Критерии успеха: Снижение числа однотитипных вопросов. Бот корретно отвечает на вопросы из "Золотого набора". 

### 1.2 Целевая аудитория и пользователи  
-  Пользователи
   1) Абитуриенты
   2) Родители абитуриентов
   3) Сотрудники приемной комиссии
-  Сценарий использования: текстовый чат в Telegram в формате вопрос -> ответ+источники
-  Нагрузка 50-100 пользователей в день. Пиковые часы: вечер будних дней, выходные

### 1.3 Ограничения и допущения  
-  Что нельзя делать:
   1) Чат-бот не дает юридических консультаций
   2) Не собирает персональные даннык(ФИО/паспортные данные/телефон и тд)
-  Допущения:
   1) Все документы берутся исключительно из официальных источников(не заглядываем на сайты консультация поступление и прочее)
   2) Обновление базы знаний происходит периодически(не в реальном времени)
- Репутационные риски:
   1) Ошибочный или устравеший ответ может привести к репутационным потерям => необходимо всегда ссылаться на источники, чтобы пользователь мог сам проверить достоверность

## 2. Архитектура решения  
### 2.1 Общая схема  
-  Архитекутра: Telegram чат -> BotApi(Aiogram) -> RAG -> Векторная DB(FAISS) + JSONL чанки -> LLM -> готовый ответ 
-  Компоненты и роли:
   1) Telegram чат: принимает сообщения
   2) BotApi: long-polling, авторизация в Telegram по токену
   3) RAG: эмбеддинг запроса -> retriever -> Сбор контекста+промт -> generation
   4) Векторная DB(FAISS): Локальное хранение, Поиск по Эмбеддингам чанков
   5) JSONL чанки: хранение текста и метаданных
   6) LLM: Генерация ответа
- Буду спрашивать со всех: где лежит бд, когда мы в неё стучимся, где лежит промпт, в каком порядке обрабатываем пользовательские запросы?
  1) БД лежит локально(FAISS)
  2) Стучимся при вопросе и обновлении данных
  3) В репозитории проекта
  4) в порядке: стром эмбеддинг -> retrieval -> Cбор контекста -> generation -> возвращаем ответ

### 2.2 Хранилище знаний / документооборот  
-  Источники знаний: Документы и правила приема ВШЭ(https://ba.hse.ru/docs), РСОШ(https://rsr-olymp.ru/) 
-  Документооборот. Загруженные документы проходят через очистку от ненужной информации с помощью LLM с сохранением метаданных(название, URL, страница)
-  Обработанные документы преобразуются в векторные представления и сохраняются в соответствующей веткорной базе данных

## 4. Модель и генерация  
### 4.1 Выбор LLM и промптинг  
-  Берется open-source модель развернутая локально(Mistral, Qwen, DeepSeek и подобные) 
-  Причина выбора
   1) Локальное развертывание => нет утечек
   2) Все LLM хорошо работают с русским и отлично работают с текстом
-  Промтинг:
   1) Входные данные: Исходный запрос пользователя в чат боте
   2) Контекст: Некоторое количество k наиболее подходящих фрагментов из векторной дата базы
   3) Инструкции: Отвечать только на основе контекста, если информации нет, явно сообщить об этом, не выдумывать факты, ответ в нейтральном стиле
   4) Формат ответа: краткий ответ на русском языке + список источников
- Ограничения: Пока не особо понятно, в зависимости от выбранной LLM модели надо тестить

### 4.2 Контроль качества ответов  
-  Метрики
   1) Покрытие
   2) Точность
   3) Удовлетворенность пользователя
   4) Ручная оценка с помощью "Золотого набора"
-  Оценка ошибок
   1) Галлюцинации
   2) Вне контекста
   3) Лишняя вода в ответе
-  Механизмы контроля
   1) Ручной ревью на основе "Золотого набора"
   2) Логирование
   3) Fallback, когда нет нужного контекста отвечаем нейтрально
   4) Эверестика: строгий запрет на ответ без источников

## 5. UX / пользовательский опыт  
### 5.1 Сценарии взаимодействия  
-  Основные сценарии
   1) Приветствие + примеры вопросов
   2) вопрос -> ответ
   3) уточнение(Уточните город/программу и тд)
-  Исключительные сценарии
   1) нет ответа -> ответ: 'не знаю'
   2) вопрос вне контекста -> ответ: 'не знаю'
   3) техническая ошибка -> ответ: 'произошли технические шоколадки, попробуйте позже'

### 5.2 Диалоговая логика  
-  Режим single-turn(все вопросы независимы, исключение сценарий уточнения)
-  Контекст: 1 вопрос для возможного уточнения
-  Стиль ответа: русский язык, короткий, деловой, только факты

### 5.3 Метрики UX  
-  Время ответа
-  Сбор фидбека пользователей(лайк/дизлайк на каждом сообщении)
-  Доля успешных диалогов(пользователь не переспрашивает одно и тоже)
-  Логирование бота для проверки качества необходимо

## 6. Безопасность, соответствие и этика  
-  Персональные данные: не сохраняем и не запрашиваем(у бота не будет функционала по ФИО найти человека в списках олимпиад и указать шансы поступления)
-  Устранение вредоносного/нежелательного контента, фильтры: 
-  Прозрачность: чат-бот должен явно сообщять пользователю, что является автоматическим помощником и может ошибаться
-  Бот не дает советы и консультации. Критически важную информацию рекомендуем проверять
